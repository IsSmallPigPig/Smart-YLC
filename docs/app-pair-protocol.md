# 手机 App ↔ 电脑 配对传输协议 v1

手机端还没开发，这份文档就是双方的契约。App 按本文实现，能通过
`tests/test_lan_pair_protocol.py` 的接口语义即视为对齐。

## 一句话流程

同一 Wi-Fi 下，App 扫电脑上的二维码 → 报上双方相同的配置提取码换会话 token →
问电脑哪些档案已经有了 → 只传缺的那些 → 报进度 → 结束。

手机和电脑不在同一网络时走中转：App 把 PDF 按 3MB 分片传到中转站，电脑端自动
轮询取回。配置提取码在两条路上是同一个——它既证明「相同配置」，也是中转通道标识。

## 0. 约定

-  transports：仅 HTTP/1.1，明文（局域网内）；所有请求必须来自私有网段
  （192.168/10/172.16-31/127），公网来源直接 403。
- 编码：请求体 JSON 用 UTF-8；文件正文是 PDF 原始字节。
- 所有响应都是 JSON，`ok` 为 `true` 表示成功。
- 文件大小上限单份 40MB（超了返回 413）。

## 1. 二维码载荷

电脑弹窗里的二维码内容是一个 URL，浏览器和 App 共用同一张：

```
http://10.12.16.118:8765/?k=A1B2C3&v=1
```

| 参数 | 含义 |
|---|---|
| `k` | 6 位十六进制配对码，大小写不敏感 |
| `v` | 协议版本，当前 `1`；App 遇到更高版本应提示升级 |

App 解析出 `host` / `port` / `k` / `v` 后，所有 API 都请求同一个 `host:port` 根路径。
二维码每次「开始接收」都会刷新配对码；旧的码在服务重启后失效。

## 2. 端点

### 2.1 配对 — `POST /api/pair`

请求体：

```json
{"pin": "A1B2C3", "device": "张三的手机", "configCode": "ABC234"}
```

- `pin`：二维码里的 `k`。
- `device`：可选，App 自报设备名，仅用于电脑端界面显示，最长 60 字符。
- `configCode`：**相同配置的判据**。App 里填的云端备份提取码（6 位，字符集
  `A-Z2-9`）。电脑配了云端档案时必填且必须一致；电脑没配时可省略。

响应：

```json
{"ok": true, "token": "随机会话凭证"}
```

两种拒绝都是 `403`，靠 `error` 区分：

```json
{"ok": false, "error": "pin", "reason": "配对码不对，刷新电脑上的二维码"}
{"ok": false, "error": "config", "reason": "手机与电脑的配置提取码不一致..."}
```

App 按 `error` 给提示：`pin` 让用户刷新二维码，`config` 让用户核对提取码。
`token` 后续所有请求都要带。配对码不作废——同一张二维码允许配对多次（失败重试），
也兼容浏览器网页继续用它上传。凭证只在本次服务生命周期内有效，服务重启或点
「结束」后失效。

**为什么用提取码当配置身份**：它是项目里唯一现成的、两端能共享的凭据，且同一个码
直接作为中转通道标识——局域网配对和中转传输不必各造一套身份。代价是知道码的人
能配对，这与云端备份的信任模型一致（码即授权），仅限信任的设备间使用。

### 2.2 查已有档案 — `POST /api/manifest?token=<token>`

无请求体（或空 `{}`）。响应：

```json
{"ok": true, "digests": ["sha256...", "sha256..."]}
```

`digests` 是电脑「同步自手机」目录下所有日期目录里已落盘 PDF 的 SHA-256 列表。
App 先算自己每个 PDF 的 SHA-256，凡是出现在这个列表里的就跳过，不上传。

这一层去重很关键：同一份档案上周传过，这周就不该再占一遍带宽。
判重只看内容摘要，与文件名无关——改过名的同一份文件也会被跳过。

### 2.3 上传一份 — `POST /api/upload?token=<token>&name=<文件名>&sha256=<摘要>`

请求头 `Content-Type: application/pdf`，请求体是 PDF 原始字节。

- `name`：手机上的文件名，URL 编码。必须是 `.pdf` 结尾，其它类型返回 `rejected`。
- `sha256`：App 算的文件摘要（小写十六进制）。电脑端记录它用于对账，不重新校验
  内容一致性——判重依赖 2.2 的清单，传输损坏由 App 在传完后自行校验。

响应：

```json
{"ok": true, "status": "ok", "note": "已保存", "name": "张三+13800138000+入团志愿书.pdf"}
```

| `status` | 含义 | App 该怎么处理 |
|---|---|---|
| `ok` | 落盘成功 | 计入已完成 |
| `duplicate` | 内容已在电脑上 | 计入已完成，不必重试 |
| `need_rename` | 已保存但文件名不合规 | 计入已完成，提醒用户改名 |
| `rejected` | 非 PDF 或写入失败 | 不重试，`note` 里有原因 |

文件名不合规（不是「姓名+手机号+入团志愿书.pdf」）的文件**照常保存**，
只是标 `need_rename`——不静默丢。

### 2.4 查进度 — `POST /api/status?token=<token>`

响应：

```json
{"ok": true, "received": ["已收到的文件名", "..."]}
```

App 每传完几份查一次，用来更新界面进度；也可在全部传完后对账——
本地清单减去 `received` 就是没传成功的，可选择性重试。

### 2.5 结束 — `POST /api/done?token=<token>`

响应：

```json
{"ok": true, "received": 12}
```

通知电脑传输结束，会话随即作废，之后再用这个 token 请求会返回 `401`。

App 首轮批量传输**不调用**这个接口：配对信息（地址、配对码、token、设备名）会落盘保存，
退出配对页后继续沿用同一条会话，后续新拍的档案直接上传。会话由电脑端接收服务管理：
关掉弹窗或空闲超时后 token 自然失效，App 收到 `401` 时标记「连接已断开」并提示重新配对。
只有用户在 App 里主动解除绑定，或明确结束一次性传输，才调用 `/api/done`。

## 3. App 侧状态机

```
扫码 → 解析 URL → POST /api/pair（带 configCode）
          ├─ error=pin    → 提示刷新二维码
          └─ error=config → 提示核对提取码
                       │成功
                       ▼
                 拿到 token
                       │
              POST /api/manifest
                       ▼
         算出本地 PDF 清单，过滤掉 digests 里已有的
                       ▼
       逐个 POST /api/upload（可并发，见下）
                       ▼
              POST /api/status 对账
                       ▼
         保存绑定到本机，保持会话供后续新档案上传
                       ▼
         主动解除绑定时才 POST /api/done 结束

若连不上二维码里的 host:port（手机用流量、两边不同网）：
  转第 9 节中转流程，用同一个 configCode 作为中转提取码。
```

## 4. 并发与顺序

- 上传可以多份并发，但同一份的字节必须连续发完（单请求单文件）。
- 电脑端用多线程 HTTP 服务，落盘函数按文件名串行处理；同名不同内容的
  两份会各自加 `(2)`、`(3)` 后缀，不会互相覆盖。
- 建议并发度 3～4；太高的并发在手机上只是排队，收益有限。

## 5. 错误码

| HTTP | 场景 |
|---|---|
| 400 | 请求体缺失或无法解析 |
| 401 | token 无效/已结束，需重新扫码配对 |
| 403 | 非私有网段、配对码错误（`error=pin`）、配置提取码不符（`error=config`） |
| 404 | 不存在的路径 |
| 409 | 中转文件分片缺失、大小或摘要不符（`action=finish`） |
| 413 | 文件超过单份上限（局域网 40MB；中转分片超过 3MB） |
| 429 | 中转站请求过于频繁 |
| 500 | 服务端异常 |
| 507 | 中转站文件数达上限，需电脑接收清理 |

## 6. 安全边界（说清楚，免得误解）

- 配对码 6 位十六进制、扫码即授权，拿到码的人能配对——这和把家里 Wi-Fi 密码
  告诉别人是一个级别，仅限信任的局域网环境使用。
- 服务只监听局域网、只接受私有网段请求，不映射到公网。
- App 不上传配对码以外任何身份信息；`device` 只是给人看的备注。
- 协议不提供加密。局域网是信任边界，若在不信任的网络（如咖啡馆公共 Wi-Fi）
  使用，应先隔离网络。

## 7. 与旧网页上传的关系

旧的浏览器流程（`GET /` 打开网页、手动选文件、`POST /upload?k=`）保留不变，
仍是配对码鉴权。二维码加了 `v=1` 参数只给 App 看，浏览器忽略它。
两条路并存：App 扫码自动传是主流程，浏览器手动选是兜底。

## 8. 落盘与后续处理（电脑端）

收到的 PDF 存到 `~/同步自手机/YYYY-MM-DD/`，并把该目录登记为来源目录，
上传页下一次扫描自动发现。文件名解析、页数检查等沿用现有上传检查逻辑，
不在这套协议里重复实现。

## 9. 中转兜底（连不上局域网时）

手机用流量、或两边不在同一网络时，局域网那条路不通。此时用同一个配置提取码走中转站。
服务端实现在 `server` 分支的 `netlify/functions/archive.mts`，默认地址
`https://smartylc.netlify.app`（取自电脑端云端备份配置里的 server 字段）。

### 9.1 为什么分片

Netlify Functions 的请求和响应都限制在 6MB。参考档案单份 1.2～8MB，整份收发会被
网关拒绝。所以每片 3MB，上传和下载都按片走；服务端 `finish` 时合并并校验 sha256，
通过才标记可读。

### 9.2 端点（单端点 + action 参数）

所有请求打到 `/api/archive?id=<提取码>&action=<动作>`。提取码 6 位，字符集 `A-Z2-9`。
写操作额外在头里带 `X-Owner-Key: <64 位 hex>`——它是建档时手机自己生成的私钥，
服务端只存哈希；只有它能写和删，别人拿提取码也只能读。

| 方法 | action | 参数 | 说明 |
|---|---|---|---|
| GET | `list` | — | 返回待收文件元数据：`{ok, files:[{id,name,size,sha256,parts,uploadedAt}]}` |
| PUT | `init` | body `{id,name,size,sha256,parts}` | 声明一份文件；同名同摘要已存在就直接返回 `exists:true` |
| PUT | `part` | `file=<id>&part=<序号>`，body 为原始字节 | 传一片，≤3MB |
| PUT | `finish` | `file=<id>` | 合并、校验大小和 sha256，通过才标记可读 |
| GET | `pull` | `file=<id>&part=<序号>` | 取一片，响应为原始字节 |
| DELETE | `clear` | `file=<id>` | 删云端副本，幂等 |

`id` 由手机生成，字符集 `[0-9A-Za-z_-]{1,64}`（用 UUID 去掉横线即可）。
单份上限 200MB / 100 片；一个提取码下最多 500 个文件，满了要先让电脑接收清理。

### 9.3 App 侧流程

```
连接 /api/pair 超时或失败
   │
   ▼
用 configCode 当提取码，GET /api/archive?action=list
   │
   ├─ 列出待收文件；对照电脑已收摘要（可让电脑经局域网告知，或全部重传由电脑判重）
   ▼
对每份 PDF：计算 sha256 → PUT init → 逐片 PUT part → PUT finish
   │
   ▼
完成。电脑端弹窗在无局域网地址时会自动每 5 秒轮询 list，
发现新文件就拉回、校验、落盘，并删除云端副本。
```

### 9.4 降级判定

电脑端的判断很简单：**没有局域网地址时**自动切中转轮询（前提是配了云端档案）。
所以 App 不必通知电脑"我走中转了"——电脑只看自己有没有可分享的地址。

反过来，App 的判定是：**连不上二维码里的 `host:port`**（超时即认定）就走中转。
两条路都要求填同一个 configCode，这是它们能对接的前提。

### 9.5 完整性

电脑拉回每份文件后校验 sha256，与 `list` 里的摘要不符就不落盘、记入 `rejected`；
落盘成功后才调 `clear` 删云端副本。`clear` 失败不回滚本地文件——本地才是最终存档，
云端残留只会导致下次重复拉取，而重复拉取会被判重跳过。

## 10. 局域网自动发现（v1，可选）

手机不必先扫码：同一 Wi-Fi 下广播一个探测包，电脑直接应答设备信息。
发现只解决「找到哪台电脑」，配对码仍由电脑生成、随应答带回；提取码不参与。
拿不到应答时退回扫码或手动输入，两条路径的配对接口完全相同。

### 10.1 传输

| 项 | 值 |
|---|---|
| 协议 | UDP |
| 端口 | 8766（HTTP 上传走 TCP 8765，分开便于抓包区分） |
| 探测包 | 广播到 `255.255.255.255:8766`，载荷为 ASCII 字符串 `SMARTYOUTH/1` |
| 应答 | 单播回探测包的源地址 |

### 10.2 应答载荷

```json
{
  "service": "smartyouth",
  "v": 1,
  "name": "AnkoQAQdeMacBook-Air",
  "port": 8765,
  "pin": "A1B2C3"
}
```

- `port` 是本次 HTTP 服务的真实端口：8765 被占用时系统会另分配，不能假定固定值。
- `pin` 是本次服务的短期配对码，与二维码里 `k=` 的值相同，用于 `POST /api/pair`。
- 不含 `configCode`：它参与云端备份加密，只在用户手动输入时使用。
- `name` 取主机名去掉域名后缀，仅用于界面显示。

### 10.3 两端行为

- 电脑：服务启动时在 8766 起 UDP 应答线程，`stop()` 时关闭；端口被占用则跳过，
  扫码照常可用。
- 手机：进入「传到电脑」页后广播一次、收约 1.2 秒，每 4 秒重复；按来源 IP 去重，
  点卡片直接用应答里的 `base + pin` 走 `POST /api/pair`。
- 手机与电脑不在同一网段、或路由器过滤广播时收不到应答，界面显示「没发现同一
  Wi-Fi 下的电脑」，此时扫码与手动配对仍是完整可用的兜底。
