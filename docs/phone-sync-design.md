# 手机 → 电脑档案同步：局域网优先，中转兜底

## 结论先行

| 需求 | 可行性 | 依据 |
|---|---|---|
| 局域网直传（同 Wi-Fi 浏览器上传） | **已实现** | `app/services/lan_share.py`，标准库 HTTP 服务 + 口令 + 只认私有网段 |
| 手机自动发现电脑（像 LocalSend） | **浏览器做不到** | 浏览器无局域网发现权限；需自建 App 走 mDNS/UDP 组播，成本与维护不划算 |
| Netlify 直传 10MB 以下 PDF | **不可行** | 函数请求体硬上限 6MB，二进制 base64 后实际约 4.5MB；参考档案最大 7.9MB |
| Netlify 分片中转 PDF | **可行（兜底）** | Blobs 单对象上限 5GB，分片 PUT 再合并可绕开请求体限制 |
| 同步完删云端 | **可行** | 一次 DELETE 调用 |

默认走局域网：同一 Wi-Fi 下几十份 PDF 是内网带宽直传，零流量、零等待、不依赖
任何服务端配额。中转只在「随手用手机流量、两边不在一个网络」时才用。

## 局域网直传怎么工作

1. 用户在上传页点「手机同步」，电脑起一个本地 HTTP 服务（默认 8765，被占用则
   由系统分配），只接受 192.168/10.x/172.16-31/127. 来源的请求；
2. 对话框显示二维码与完整地址，地址里带 6 位十六进制口令——扫到地址就等于拿到
   口令，别人不知道地址就进不来；
3. 手机浏览器打开上传页，多选 PDF，逐个 POST 到 `/upload`，页面上有逐份进度；
4. 收到的文件交给 `phone_sync.receive_pdf` 落到 `~/同步自手机/<日期>/`，
   SHA-256 判重、同名不同内容加序号、命名不合规仍保存但提示改名；
5. 落盘目录自动登记为来源目录，上传页立刻刷新，档案出现在待上传列表；
6. 界面自动发送「已收到」提示，30 分钟无活动自动停止接收。

实测：本机服务端到端（页面、上传、错口令拒绝、超限拒绝、重复判重）见
`tests/test_lan_share.py`，8 个用例涵盖以上路径。

### 浏览器发现不了电脑这件事

LocalSend 用 UDP 组播互相广播，浏览器没有这个能力。替代做法只有两种：
电脑显示地址/二维码让人扫（已实现），或者自建移动端 App（需要额外分发与维护）。
后者对「一位老师给自己传几十份 PDF」的场景收益不足。

## 中转（兜底）：为什么直传不行

参考档案 49 份实测：单份 1.25–7.9MB，均值 3.3MB。
Netlify Functions 的请求/响应是 **buffered 6MB**，二进制走 base64 有约 30% 开销，
实际可上传上限约 **4.5MB**。7 份档案超限，直传会被网关直接拒绝（413），
不是函数代码能绕过的。

Blobs 本身单对象能到 5GB，但数据进出都要经过函数那道 6MB 的墙。

## 分片协议（推荐）

沿用现有 `server` 分支的 Netlify 函数和 v2 所有权模型（owner key + 403 越权拒绝），
新增三个端点：

```
POST /api/archive/init      {id, size, parts, sha256}  -> 建立会话，返回 uploadId
PUT  /api/archive/part      {uploadId, index, data}    -> 存一片（每片 ≤ 3MB）
POST /api/archive/finish    {uploadId}                  -> 合并成 Blob，校验 sha256
GET  /api/archive/list      ?since=<ISO>               -> 待同步清单（只含元数据）
GET  /api/archive/pull      ?id=<id>                    -> 分片拉回（响应流式）
DELETE /api/archive/pull    ?id=<id>                    -> 同步完成后删除
```

约束：
- 分片 3MB（base64 后约 4MB，留出余量），一份 7.9MB PDF 约 3 片；
- 会话本身存 Blobs，带 `expiresAt`，避免半截会话堆积；
- `finish` 时校验总 sha256，不一致直接丢弃，不让损坏文件落到电脑；
- 所有权：只有建档的 owner key 能 `finish` / `delete`，他人只能 `pull`。

## 电脑端落盘

收到全部分片并校验后，调用 `app.services.phone_sync.receive_batch()`：

- 落点固定为 `~/同步自手机/YYYY-MM-DD/`；
- 用 SHA-256 判重，同名同内容不落第二份；同名不同内容自动加 `(2)` 后缀，不覆盖；
- 文件名不合规的照常保存，但列入 `rejected` 提示用户改名——不静默丢；
- 落盘后把该目录登记进 `workspaceDirs`，上传页下次扫描自动发现，无需手动加来源目录。

## 同步完成后删云端

电脑端确认落盘 + 结构检查通过后，对每个 id 调 `DELETE /api/archive/pull`。
失败不回滚本地文件（本地才是最终存档），只记日志待重试。

## 为什么不选公网映射

Netlify 只做静态托管 + 无状态函数，没有反向隧道。要让公网请求打进家里电脑，
必须额外跑 `cloudflared tunnel` 或 frp 常驻进程，并配动态域名/鉴权。
这引入一台必须一直开机的电脑、一个第三方隧道账号和一套新的故障点，
与「垃圾 CPU 也能跑、尽量零依赖」的目标相悖。分片中转用现成的 Netlify 站点，
不需要新增任何服务。

## 档案内容校验：分层策略

参考档案 49 份 / 637 页实测全部是纯扫描图（零文本层），因此分两层：

**第一层：结构检查（默认，纯 CPU 毫秒级）**
`app/services/archive_exam.py`，用 PyMuPDF 低分辨率缩略图 + numpy 灰度统计，
判页数、缺图、分辨率过低、空白页。49 份参考档案（均 13 页）实测零误报；
灰底扫描的"备注"页不会被误判为破损。这是"页面破损/漏页"的答案。

**第二层：OCR 姓名核对（可选，用户点「核对信息」才跑）**
`app/services/archive_ocr.py`，用 rapidocr-onnxruntime（约 30MB 模型，纯 CPU，
onnxruntime 推理），只识别封面第 1 页的"申请人姓名"，与文件名、在线名单比对。

可选依赖：`pip install rapidocr-onnxruntime`。未安装时界面给出明确提示，
不假装通过。没有把它写进 requirements.txt，避免所有平台打包都背上 30MB
模型——只有需要核对信息时才装。

**手写 OCR 的准确率边界（实测）**：12 份样本中 8 份准确识别，4 份误识
（"炯"→"回"、"玮"→"王玮"、漏字）。因此系统只做「疑似不一致」提示，
绝不自动判定档案错误或拦截上传；未识别出姓名时会明确要求人工核对漏填，
不会静默放行。这是"信息是否与在线数据一致"能做到的可靠程度。

## 逐格检查（第三层）：表格里哪些格子没字

`app/services/form_cells.py`，OpenCV 形态学 + 连通域，纯 CPU 单份 0.1~0.7 秒。

1. 自适应阈值抽出表格线，用线掩膜的反向做连通域——每个闭合区域就是一个真实
   单元格。合并单元格天然是一格，不会切出假空格（这正是「按行切分网格」的做法
   在这些扫描件上失效的原因）。
2. 每格数「字符连通块」（面积 ≥ 8px）。空白格 0 块；填一个「1」也有 1 块，
   所以判据不受字号粗细影响——用墨迹**面积**判会把极细的手写数字误判成空白。
3. 三条同时成立才算可疑空格：本格 0 块、同一行还有其他有字的格、同列下方还有
   内容。第三条专门用来排除表格自带的空白填写行（备用行成串出现，真正的漏填
   是孤立的）。
4. 结论只作提示：预览页把空格用红框画在页面上，人一眼核对。不自动判异常、
   不拦截上传——扫描件的倾斜、透印、光斑都可能造成误判。

参考档案 49 份（13 页/全部扫描图）实测：98 处提示、约 2 处/份，全部落在表格
内的空白格；阳性对照（把「籍贯」取值格涂白）能稳定抓到 1 处。

依赖 OpenCV（`opencv-python-headless`，Win7 包用 4.8.1.78，最后一个支持 py3.8）。
未安装时该层跳过并在界面写明原因，不假装通过。
