# 移动端与桌面端业务比对

对照对象：桌面端（`main` 分支，PyQt5，7 个页面 + 3 个子系统）与 Android 端本仓库（10 个页面）。
结论先说：移动端定位是「现场拍摄上传 + 名单核对」的轻量工具，桌面端是「全量管理 + 统计 + 导出」的台账工具。重合的是名单查看与档案上传，缺口集中在组织管理、统计仪表盘、导出与账号运维。

## 一、页面级对照

| 桌面端 | 移动端 | 实现情况 |
|---|---|---|
| 工具首页：4 个统计磁贴、上传进度圆环、4 条异常横条、转接申请摘要 | 首页：状态主卡、状态条、团员/待处理两卡、4 格异常、扫描入口 | 部分。缺圆环、支部数量、转接申请 |
| 组织状况：8 张卡（团员概览环形图、异常团员、欠缴、没有档案、上传进度、待办数据、支部异常排行、账号状态）+ 异常名单卡片流 + 导出 | 无独立页 | 缺失。仅首页 4 格异常与名单筛选可替代局部 |
| 组织管理：学部→年级→支部→团员树、支部详情、团员 17 字段展开、访问支部 | 名单页平铺全量，搜索与 6 个筛选，详情弹窗 6 个字段 | 部分。无支部层级、无支部详情、字段不全、无浏览器 |
| 上传档案：目录扫描、命名/页数/重复/空格四类预检、压缩到 9.5MB、逐支部上传与自动审核、异常区 | 扫描：相机拍摄、文档边缘检测、裁边、按姓名命名、保存与上传 | 形态不同。移动端以拍摄替代目录扫描，缺预检与批量 |
| 系统消息：分类页签 + 已读/未读/全部 + 每页 12 条 + 全部已读 + 跳转支部处理 | 站内信：4 个分类、未读标记、详情弹窗 | 部分。无分页、无全部已读、无跳转 |
| 系统配置：账号表 8 列（导入/测活/删除/届别）、名单导入、编号规则、外观、工作目录、通知、备份、更新 | 我的：账号管理、刷新名单与消息、默认画面处理、保存后立即上传、主题、关于、退出 | 部分。缺批量导入、测活、编号规则、通知、备份、更新 |
| 访问支部：多标签内嵌浏览器，每支部独立会话 | 无 | 缺失 |
| 导出数据：5 类内容 × 分班/合并 × 每项一表/合成一表 | 无 | 缺失 |
| 云端备份：提取码 + 密码加密，可覆盖自己的档案 | 云同步页 | 部分，待逐项核对 |
| 登录公告、已知问题面板、使用引导 | 无 | 缺失 |
| 手机接收：局域网接收手机拍的 PDF | 扫描后直接上传 | 移动端替代了桌面端的接收端 |

## 二、人员卡片字段对照（你点名的那张卡）

桌面端组织管理里展开一名团员是 **17 个字段**，移动端详情弹窗是 **6 项**。

| 桌面端字段 | 移动端 |
|---|---|
| 实名认证 | 有 |
| 报到资料状态 | 有 |
| 电子志愿书 | 有 |
| 未交团费（元）+ 累计未交月份 | 有，合并成一行 |
| 所属团支部 | 有 |
| 入团时间 | 有 |
| 电子团员证照片 | 缺 |
| 政治面貌 | 缺 |
| 全日制学历 | 缺 |
| 职业 | 缺 |
| 工作/学习单位 | 缺 |
| 报到申请时间 | 缺 |
| 报到审核时间 | 缺 |
| 资料修改时间 | 缺 |
| 资料修改审核时间 | 缺 |
| 奖励状态 | 缺 |
| 团员编号 | 缺（列表与详情都不显示） |

移动端 `Member` 数据类本身只有 13 个字段，其余字段在解析阶段就被丢掉了，不是界面没画出来。要补齐得改 `MemberParser` 与缓存写入两处。

## 三、口径差异（会直接影响真机验收数字）

1. **信息错误的判定范围不同。** 桌面端把「收入不含学生无收入」也算信息错误；移动端 `Member.identityOk` 只看实名状态。同样的数据，移动端的「信息错误」会少于桌面端。
2. **实名校验有字符串陷阱。** 两端都用 `contains("通过")` 判断，遇到「未通过」「校验不通过」会误判为合格。本次已把移动端收紧为「含通过且不含不通过」，桌面端 `check_rules.py` 仍是旧写法，待确认。
3. **异常人数去重口径不同。** 桌面端按 `member_id` 去重后取并集；移动端 `count { it.abnormal }` 按行计数。同一人重复入册时数字会偏大。
4. **支部数量缺失。** 桌面端首页有「覆盖 N 个支部」，移动端没有对应指标。
5. **电子团员证未采集无法显示。** 移动端不保存该字段，桌面端该指标本身也存在枚举不匹配的问题（判据查「已采集」，枚举里只有「审核通过」），两端都需要先定口径。

## 四、测试数据

位置：`testdata/`

| 文件 | 内容 |
|---|---|
| `accounts.csv` | 20 个支部账号，密码统一为 `测试账号-勿用于真实登录` |
| `members.csv` | 123 名团员，20 列中文表头，可直接当核对名单 |
| `members.json` | 同一批数据的桌面端字段名版本 |
| `roster/<账号>.json` | 移动端本地名单缓存格式，每个账号一份 |
| `desktop-config.json` | 桌面端整份配置，含账号、成员缓存、站内信 |
| `accounts.xml` | 移动端账号表（SharedPreferences），真机注入用 |
| `stress/` | 压测包：单个账号 `ylc00000` 挂全部 123 人 |
| `generate.py` | 生成脚本，固定种子 20261120，可重跑 |

移动端只显示当前账号所属支部的名单，20 个账号分散在 20 个支部，切账号才能看全 123 人。要看 123 人的完整列表，注入 `stress/` 里的账号与名单。

### 分布

20 个支部，每班 5 到 9 人，合计 123 人。支部名带编号（`12401` 高一 1 班），最后一个支部是超长名「高三实验班（创新人才培养改革试点）」。全名单姓名不重复。

| 类别 | 人数 | 构成 |
|---|---|---|
| 已上传档案 | 106 | 99 人档案齐全，另 7 人报到环节有问题但志愿书已传 |
| 未上传 | 17 | 9 人「三样都没做」，8 人「已报到但没传志愿书」 |
| 没有报到 | 13 | 9 人从未报到，4 人报到待审核 |
| 没有档案 | 11 | 8 人状态为「电子志愿书待上传」，3 人为「已报到,电子志愿书未上传」 |
| 信息错误 | 3 | 实名「校验失败」；另有 3 人缺手机号、2 人收入未填，移动端不计入这一类 |
| 欠缴团费 | 6 | 1 到 18 个月不等，金额 0.5 到 54 元 |

四类互不重叠，异常合计 33 人，与首页「待处理」应对得上。

边界样本：超长姓名 1 个、带间隔号姓名 1 个、带括号姓名 1 个、缺手机号 3 人、同号 2 人（`13800138000`）。

### 注入真机

```bash
# 账号表与名单缓存推进应用私有目录，需要 debug 包（可 run-as）
adb push testdata/accounts.xml /data/local/tmp/accounts.xml
adb shell run-as com.smallylc.smartyouth cp /data/local/tmp/accounts.xml shared_prefs/accounts.xml
adb push testdata/roster/. /data/local/tmp/roster/
adb shell run-as com.smallylc.smartyouth cp -r /data/local/tmp/roster/. files/roster/
adb shell am force-stop com.smallylc.smartyouth
```

会覆盖真机上已有的账号与名单缓存，执行前先备份 `shared_prefs/accounts.xml` 与 `files/roster/`。

## 五、本轮实测发现并修复的问题

在模拟器上用注入数据跑通了名单、筛选、详情，过程中修掉三处：

1. **名单缓存回读丢失报到状态。** `Repo.saveCache` 写的是 `reportStatus`，`MemberParser` 的别名表只有 `auditStatus` 与 `reportDataStatus`，于是缓存里的报到一个都读不出来，界面把正常团员全标成「未报到」。已补上别名，并把「缓存写入键必须被解析器识别」写成 `scripts/lint_patterns.py` 的规则。
2. **实名判断把「未通过」当合格。** `realNameStatus.contains("通过")` 对「未通过」「校验不通过」都返回真。已收紧为「含通过且不含不通过」。桌面端 `check_rules.py` 还是旧写法，需要确认是否同步修。
3. **`LanDiscovery` 编译不过。** `socket.receive(packet)` 返回 Unit，却被当成 DatagramPacket 取 `.data`。全量编译才会暴露，增量构建一直掩盖着。

另外改了名单页的两处表达：筛选标签带人数（未上传 17、信息错误 3、没有报到 13、没有档案 11、欠费 6），标题在筛选时显示「团员 3 / 123」，避免筛完看不出结果多少。

## 六、真机验收顺序

按「不依赖站点」到「依赖站点」排：

1. **名单渲染**：注入后打开名单页，123 人是否全出、滚动是否掉帧、长姓名与超长支部名是否截断得体。
2. **搜索与筛选**：搜「欧阳」应命中 1 人；搜手机号 `13800138000` 应命中 2 人；六个筛选的人数是否与上表一致。
3. **详情卡**：逐项核对 6 个字段的文案与颜色；确认缺手机号时不会显示空白行。
4. **分类计数**：首页 4 格异常数应等于筛选后的列表人数（信息错误 3、没有报到 13、没有档案 11、欠缴 6）。
5. **站内信**：20 个账号各 3 条，切分类与未读状态是否正常。
6. **扫描链路**：需要真实站点，等维护结束再测。
